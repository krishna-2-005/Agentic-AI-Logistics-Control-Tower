### Stream equals batch (D1-D2)

*Generated by `python -m src.ml.stream_validation` -- regenerate rather than editing numbers by hand.*

Generated: 2026-09-08T14:36:35+05:30

The invariant Week 5's gate rests on: an identical leg must score identically whether it is read from `features_v1` in batch or arrives as a JSON event on the stream. Both paths here run the same champion `PipelineModel` (`data/models/champion`, promoted by D-029's retrain loop).

| Check | Result |
|---|---|
| Legs compared | 500 |
| Identical predictions | **500 of 500** (100.0%) |
| Largest absolute difference | **0** min |
| Temporal fields: carried == `schema.temporal_features()` | **500 of 500** |
| Rows the naive `datetime.weekday()` reading would corrupt | **500 of 500** |

**Every prediction is bit-identical.** The event round-trip -- `query_event` -> `json.dumps` -> `json.loads` -> rebuilt feature row -- changes nothing the model reads. That is the result this test exists to produce, and it is worth being precise about what it licenses.

#### What this does and does not license

A prediction needs 27 features. The event carries **6** of them (`planned_min`, `planned_km`, `created_hour`, `created_dayofweek`, `created_is_weekend`, `is_ftl`); the other **21** are the `corr_*`/`src_*`/`dst_*` history D-031 deliberately keeps out of the event for a broadcast join to supply. Both paths above take those from the same `features_v1` row -- which is what a *correct* broadcast join delivers by definition, and precisely the thing Mounika's streaming job (D3-D4) still has to earn.

So: this run says the **event format** is not what would break the stream. It does not yet say the streaming job is correct. The same assertion gets pointed at that job's output once it exists, and only then does the gate's claim hold end to end.

#### The day-of-week trap this test caught

The event carries the temporal features as explicit fields, but a streaming job could just as reasonably recompute them from `event_time`. Written the obvious way -- `datetime.weekday()` -- that recomputation disagrees with the carried value on **500 of 500 rows**, because Stage 4 built the feature with Spark's `dayofweek` (**Sunday = 1**, Saturday = 7) and Python's `weekday()` counts from **Monday = 0**. On a Wednesday that is 4 against 2.

Nothing raises when this happens. The model receives a number on a different scale for every event and answers confidently and wrongly -- no exception, no null, no row count that looks off. `src.streaming.schema.temporal_features()` is now the one place that conversion lives, so the streaming job and the batch pipeline cannot drift apart on it, and the row above is the regression guard. Full account: `docs/problems.md` P-39.

Full per-leg output: `benchmarks/raw/w5_stream_equals_batch.csv`, `w5_stream_temporal_check.csv`, `w5_stream_validation_report.json`.

## What the numbers above mean

**The threshold sweep says two things, and only one of them is what I set out to test.**

The one I set out to test: does 2.00× hold up now that there are models to check it
against? It does, and the reason is sharper than D-003's. The best classifier's MCC is
almost flat across thresholds (0.507 at 1.15×, 0.536 at 2.00×). Moving the
line does not create or destroy signal; it moves the alert volume, from 98% of legs to
49%. An alert for nearly every shipment is the same as no alert. That is why 2.00×
is right, and the MCC table is what shows it. The F1 table beside it is there to make the
trap visible: at 1.15× the classifier that does nothing scores 0.977.

The one I did not set out to test: **the model the stream actually alerts with is the
weakest real classifier in the table.** At 2.00× the thresholded champion scores
MCC 0.477. Logistic regression scores 0.536, and even the corridor-mean baseline scores
0.502. The champion flags 67.6% of legs when 48.9% are really delayed, and that over-alert
is the flood Krishna's bot had to shortlist and the 65.7% Mounika's replay showed. The
champion is the right *regressor*: the "+N minutes" on every alert should keep coming from
it. It is the wrong *alarm*. D-040 records the Week 6 fix: flag with a classifier, or a
recalibrated cut, chosen by MCC. It is not applied this week, because the stream, panel and
bot were all measured with the current flag, and changing it now would quietly invalidate
their numbers.

**The eval says the agent handles ten specific failure modes, 40 times out of 40.** Four
of four on every template, across two run days. That covers:
- tonnes converted;
- pieces read from words;
- a corrected weight taken over the stale one it corrects;
- origin and destination kept straight when the prose reverses them;
- questions for a weight range, an approximate count, an unnamed service and a city-only
  destination, and each question named the right field;
- the company, not the signatory, as the customer, in all 20;
- in both cases missing two fields, weight asked before service, as rule 2 requires.

**What 50 of 50 does not say.** It is a ceiling: these templates are cleaner than real
customer email, and a perfect score cannot separate a good agent from an excellent one.
Getting there took five quota days (20 calls a day), which is why the week was tagged at
40 of 50 and closed later at 50 — the count in every generated table is the count that had
actually run at the time, never a projection.

**A note on what a perfect score is worth.** 50 of 50 is a real result for these ten
failure modes and a weak one for the general question. The templates are mine, so they
test what I thought to test. The honest reading is: the agent handles every ambiguity
this set knows how to express, and the next version of this eval should be built from
email the agent gets *wrong*, not from more of what it gets right. That is Week 6's
agent-evaluation work, where the Exception Agent gets the same treatment.

**Decisions:** D-040. The shared `delay_label` helper closes the loop P-42 opened: the
training label, every regressor's thresholded prediction and the stream's fact events now
come from one function.
